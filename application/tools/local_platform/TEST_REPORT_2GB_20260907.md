# 双核 / 2GB 测试预算演练结果（2026-09-07）

## 结论

**测试执行已完成，但“所有并发请求均成功”的验收没有通过。**

在本轮受限容器中，现有 Python 后端和真实 PostgreSQL 可以启动并完成基础功能、
持续合成读写与重启后历史记录读回。没有观测到内存不足、触及内存上限或意外重启。
这些证据支持将 2GB 作为个人/小规模功能测试的起步配置，但不能承诺真实阿里云
整机、长期运行或任意数据规模都足够。

真实发现的限制是应用已有的并发保护：最终轮共 **26 次 HTTP 429**，均识别为
`Upload capacity limited`（上传/消息入口容量限制），不是 OOM（内存不足退出）。
其中开始发送消息 25 次、文件上传 1 次；没有其他 HTTP 错误或请求超时。
因此保留机器报告中的 `status=failed`、`capacity_gate_passed=false`，不写“全部通过”。
`test_workflow_completed=true` 仅表示包括资源核验、重启检查和结束清理的流程已完成。

- API 原单 worker、数据库连接池 5、数据库连接上限 30、Argon2 密码哈希强度及
  并发保护均保持不变，没有为了测试通过降低安全强度。

Docker inspect 和容器内 Linux cgroup 双重核验实际内存/CPU限额、CPU绑定、禁用
swap、无公开端口与内部网络；不是仅检查配置文件文字。
限额机制依据 [Docker 官方资源限制文档](https://docs.docker.com/engine/containers/resource_constraints/)。

## 最终轮并发结果

使用 2 个合成账号，依次模拟 1、3、5 个独立客户端。每个客户端新建独立负载会话，
不修改首次验收的两个基准会话。每轮查询会话、写入固定合成问题与回答、读回验证；
每十轮额外上传并核对一个 **49,353 字节、约 48.2 KiB** 的合成 PNG。

| 并发客户端 | 实际负载秒数 | 负载请求总数 | HTTP 200 | HTTP 429 | 其他错误/超时 | 请求 P95 延迟 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 60.000 | 694 | 694 | 0 | 0 | 28.751 ms |
| 3 | 60.004 | 2,028 | 2,027 | 1 | 0 | 39.027 ms |
| 5 | 60.048 | 2,911 | 2,886 | 25 | 0 | 55.695 ms |
| 合计 | 180.052 | **5,633** | **5,607** | **26** | **0** | 不合并分位数 |

表中不含登录、建会话和注销的 27 个准备/清理请求；计入后总请求数为 **5,660**。
P95 表示约 95% 已记录请求的耗时不超过该值，包含限流响应；它只是本机合成接口
耗时，**不是 AI 模型生成耗时，也不是公网延迟或吞吐容量承诺**。

每客户端实际完成的业务循环数：

- 1 客户端：`[165]`。
- 3 客户端：`[161, 162, 159]`。
- 5 客户端：`[139, 141, 135, 132, 133]`。

每个客户端均实际参与读写，不是仅启动了线程。合计成功完成 1,327 个完整循环，
文件上传后哈希验证通过 135 次。部分遭遇文件上传限流的循环已完成聊天读写但没有
计为完整循环，原始 HTTP 计数和各阶段统计均保留。

本轮显式启用了 `--observe-rate-limits`：429 仍计为错误并保持阶段 `failed`，
等 0.5 秒后开始新的业务循环及新请求 ID，不悄悄重放同一写请求。默认循环间隔
0.3 秒；因此这是一种**带退避的并发观察**，不是全部请求一次成功的容量结论。
只有单纯 429 才继续下一档，500/503、超时、网络、业务错误或无人参与的客户端会
阻止继续升档；本次没有这些异常。

## 发现的问题与解释

`server/platform_app.py` 的 `PlatformBoundary` 为以下两个接口共用一个
`asyncio.Semaphore(1)`（同时仅允许一个进行中的请求）：

- `/v1/rpc/chat/begin_message`：开始发送消息，**包括纯文字消息**。
- `/v1/rpc/files/upload_bytes`：文件上传。

获取名额等待超过 `0.05` 秒时，程序主动返回 HTTP 429，固定错误类别为
`Upload capacity limited`。最终实测的 26 次响应都匹配这一类别：3 客户端档
开始发消息 1 次；5 客户端档开始发消息 24 次、文件上传 1 次。

这是已存在的应用并发保护，不是这轮新引入的限制，也没有内存不足证据。**单纯
把 2GB 升到 4GB 不会自动更改这条规则**；实际发生概率还受请求节奏、CPU、磁盘
及网络影响。本轮没有做 4GB 对照实验，不宣称两种配置性能相同。

后续若需要多人密集操作，建议另行实现/检查桌面端忙碌提示、带幂等请求 ID 的有界
排队或重试策略，再复测；不能直接取消保护或无限放大并发。本次用户要求是测试，
因此**没有修改业务保护、客户端交互或云端配置**。
